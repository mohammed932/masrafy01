## Project Identity

**Masrafy** (internally "Credit Match") — Egyptian fintech loan comparison marketplace. Connects users with 20+ bank loan programs (ABK Egypt + partners) via 5-step wizard + matching engine. Four product lines: personal loans, car loans, mortgages, business loans. Free for users; commission revenue from banks. Three platforms governed by a single constitution: NestJS backend (active), Angular admin dashboard (active), Flutter mobile app (deferred until Figma).

Constitution: [.specify/memory/constitution.md](.specify/memory/constitution.md) v15.1.0

**Product scope-lock (v16.0.0 / Principle II):** Platform supports exactly FOUR retail loan categories — `personal`, `car`, `mortgage`, `business`. **The no-payslip product is an income BASIS, not a category.** v15.0.0 shipped it as a fifth category (`fast`, "Fast Loans"); v16.0.0 removed it — the same catalog name is sold against a payslip by one bank and against a grade table by another, so a category duplicates every sellable name and asks the customer to choose between two descriptions of one loan. What the bank reads is `bank_program.programType` (`income_proof` / `income_surrogate`), chosen per program; the applicant is asked the four surrogate facts *as well as* the payslip questions. **No category constrains the program type** — `PROGRAM_TYPE_INVALID_FOR_CATEGORY` is deleted. **No hardcoded capable list either:** `SURROGATE_REQUIRED_CATEGORIES` and `SURROGATE_CAPABLE_CATEGORIES` are both DELETED (not renamed). A category can sell a no-payslip program exactly when its applicants are asked one of the four facts (`question_loan_category`) — admin-configurable on `/questionnaire/categories`, with `personal` + `car` seeded as the default, so widening the product is an admin action, not a release. Removing a category requires a destructive migration that physically wipes registry entry, bank programs, and all applications + cascade (offers / decisions / activities / documents). Ghost / soft-deactivated rows = review block. Adding a FIFTH, or re-introducing no-payslip as a category, requires a constitution amendment (A26).

## Constitution Principles — Daily Rules

### Cross-Platform (NON-NEGOTIABLE)

- **I — Money is Decimal**: `Decimal` types only; floats forbidden. `BankOffer` immutable post-creation.
- **II — Banks Are Data**: no `if (programId === ...)` branches; tier resolution generic.
- **III — Typed Errors**: API returns `{ success: false, code: "CODE", meta? }`; no English to clients. Same-PR rule: backend `error-codes.ts` + Angular `error-codes.{ar-EG,en-US}.json` + Flutter ARB.
- **IV — Arabic-First**: all user text via `@angular/localize`; logical CSS only (`margin-inline-start`, never `margin-left`); test LTR + RTL on UI PRs.
- **V — Matching Engine Is IP** (v8.0.0; global pool v10.0.0; asked-weight denominator v13.0.0; all types scoreable v14.0.0): pure module. Formula + tiers in code (PR-reviewed). **Two-level weighted**, normalised over the questions the applicant was ASKED: `probability = Σ_answered(questionWeight × answerScore÷100) ÷ Σ_asked(questionWeight)` (clamped 0..1; per program the ASSIGNED question weights sum to **100** and each answer score is **0–100**). *Asked* = active + assigned to the applicant's category + visible after branching (**no type filter — every type scores, v14.0.0**). Per type, one answer → one 0–100 score, all admin DATA in the same `weights` blob: `SINGLE_SELECT` → the picked option's score · `MULTI_SELECT` → picked scores combined by the program's `aggregation` (`AVERAGE` default / `SUM_CAPPED` / `MAX` / `MIN`) · `NUMERIC` → the score of the half-open `[from, to)` **band** the value falls in (ordered, gapless, −∞…+∞, Decimal edges) · `TEXT` → **presence only** (`answeredScore`; keyword/regex scoring is forbidden). A weighted question with no rule for its type is rejected on save (`WEIGHTS_MISSING_RULE`) — it would eat denominator weight it can never earn back. Weight on a question the category never asks leaves BOTH sides (so it can no longer cap a program forever); an asked-but-skipped question keeps its weight in the denominator and earns nothing. Nothing asked → 0, never `NaN`. No ACTIVE set → `usedDefault`, persisted on the offer and rendered "Not rated", NOT `very_low`. Questions + answer options are **pure content** (label + order — NO scoring/eligibility fields) and **carry NO `category` column — one GLOBAL question pool** with a single versioned snapshot. (v12.0.0) Each question is **assigned to one or more loan categories** via the `question_loan_category` join table (many-to-many — one question can serve several), so the chosen category filters BOTH which *programs* match and which of the pool's *questions* are asked — never which *questionnaire* is served (there is one). Assignment is authoritative (assigned to nothing = asked by nobody), lives only in the join table, and is **frozen into the snapshot** (a pre-v12 snapshot carries none → reads as all categories). `GET /v1/questionnaire?category=` narrows the snapshot (unknown value → `VALIDATION_FAILED`, never a silent fallback) and apply scopes required-question enforcement to the same set. Per bank program, the admin **selects which questions it scores on** (checkbox in the per-program editor) — assignment IS the `questionWeights` key set (no join table) — plus the weights + answer scores, all admin-editable DATA stored in `ScoringWeightSet.weights` as `{ questionWeights: {questionCode→weight}, answerScores: {questionCode→optionCode→score} }` (legacy single-level rows upgrade on read). **Direct admin save** (no maker-checker; editor ID audited; atomic archive+activate). No ACTIVE set (no assigned questions) → score 0. **Eligibility gating dropped for MVP** (no salary/age/DBR/loan-amount/max-loan): every active program in the chosen category returned ranked by probability, in BOTH preview and apply (apply runs the engine with `skipEligibility`).
- **VI — PII Protection**: encrypt at rest; logs never carry PII; documents in S3 with presigned URLs; audit log append-only.
- **VII — Observability**: `X-Correlation-Id` everywhere; `/health/live` + `/health/ready`; structured JSON logs (Pino); discrete business events.
- **VIII — Brand**: `#0869C3` azure blue primary. Use tokens, never raw hex.

## Recent Changes
- 2026-08-25 (v18.4.0): MINOR — **a no-payslip product is a ROW, not a copy: `surrogate_product` archetypes, and the compound lists move onto the product that reads them.** Two problems with one root cause — the platform had no name for "a no-payslip product", so the pieces of one were scattered. (1) Compounds and compound classes lived under `/lookups`, three clicks from the only calculation that reads them: an operator filing a compound under a class had no way to see which product they had just re-priced. (2) v18.0.0 shipped with the gap stated — *"the catalog variant does not yet AUTHOR a pipeline"* — so a new no-payslip catalog name was created silently broken and stayed that way until somebody wrote a seed. Both close if the archetype is a first-class row. **New enumeration type `surrogate_product`**, reusing the EXISTING `incomeRule` + `valueSources` columns (so `catalogIncomeRulePaths` keeps its `incomeRule.` root and NO value-source marker is re-rooted, unlike `20260823130000`). New nullable `platform_enumeration.surrogateProductKey` + index — NOT `parentKey`, for three reasons that are each load-bearing: `resolveParentKey` REQUIRES a parent on create (every payslip name would become uncreatable), `enumerationParentKeys()` is one flat type-less map read by `factParentTable` (a colliding key would hand a compound a class), and the admin mirrors `PARENT_TYPE_BY_TYPE` to decide whether to render a required "Filed under" select. No FK — the reachable unique is the composite `(type, key)`, same posture as `bank_program.programNameKey`. **THE SINGLE SEAM is `programNameIncomeRules()`**: all five callers hand the finished map to `toBankProgramSnapshot` or `.get()` it, so resolving there left the engine, the mapper and every caller untouched (verified). One new pure `effectiveProgramNameRule` in `income-rule-inherit.ts` — **STRICT REPLACE, never a merge**: a merge would be a third inheritance level on a two-level system and would make "the calculation is read from the product every time" false on day one. TWO maps in the resolve, not one: a name and its product deliberately share a key (`compound_owner` is both), so a single map keyed by `row.key` would let whichever row the driver returned last silently win — pinned by a test where the two hold different rules. **Migration `20260825090000_surrogate_product_link`** creates the two pipeline archetypes by copy, links BY EXPLICIT KEY (never "whatever had a rule"), NULLs the linked names' own rule and markers, then RAISEs on four states: a dangling link, a name holding both a link and a rule, an archetype whose `steps` did not come across, and a live `bank_program` that would quote nothing.
