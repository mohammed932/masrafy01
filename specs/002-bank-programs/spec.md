# Feature Specification: BankProgram Management — Tiered Loan Product Configuration

**Feature Branch**: `002-bank-programs`
**Created**: 2026-05-12
**Status**: Draft
**Input**: User description: "Admin interface and backend API for creating, configuring, and managing bank loan programs. The reference catalog is the 20 ABK Egypt Personal Loan Programs (plus competitor catalogs like Bank NXT and the sales-floor catalog transcribed from operator notes: Blue/Plus no-docs, Self-Employed tiered-by-amount, High End wealth, Auto Loan tiered-by-down-payment). Each program has multiple tier dimensions (rate by employment type, salary category, tenor bucket, transfer type, property type, profession rank, military grade, years in practice, CD value, down-payment percent, asset value, customer-program tier, etc.). The system must also represent specialty mechanics: income-surrogate computation (when income is inferred rather than declared), variable-rate programs (CBE + spread), secured loans (multi-currency, LTV-based limits, DBR skip), buyout programs (rate delta from original loan), credit-card / auto cross-sell (with performance-history gates), fee-waiver penalties (+2% if admin fees waived), insurance-waiver penalties (+2% if mandatory life / lease insurance waived, separate from admin-fee waiver), admin-fee-waiver thresholds (waive admin fees when rate ≥ X), no-documents lending tier, large-bank-statement and minimum-assets gates for wealth tiers, and asset-value or loan-amount discounts (e.g., car price > 4M → −1% rate). Adding a new bank program OR a new bank OR a new specialty mechanism whose dimensions are already represented in the schema MUST require zero code changes."

## Clarifications

### Session 2026-05-12

- Q: When a bank program has both a base value AND tier overrides for the same dimension (e.g., rate / max loan / max tenor), which wins for a given application? → A: Most-specific tier wins with a deterministic precedence order per dimension. For pricing: `rateByTenor → rateByTransferType → rateBySeniority → rateByEmploymentType → baseRate`. For loan limits: `maxByCDTier → maxByPropertyType → maxByCityTier → maxByTransferType → maxBySalaryCategory → maxByEmploymentType → maxEGP`. For tenor: `maxMonthsBySalaryCategory → maxMonthsByEmploymentType → maxMonths`. First matching tier returns the value; if no tier matches, fall back to the base value. The platform never composes / multiplies; it always selects exactly one source.
- Q: How is concurrent-edit conflict prevented when two admins save the same bank program at the same time? → A: Optimistic version field. Each bank program carries an integer `version` that increments on every persisted save. The dashboard loads the version with the program and sends it back on save; the backend compares-and-swaps in a transaction. Mismatch → `CONFLICT_STALE_DATA` response with the current version; the dashboard prompts a reload.
- Q: How are platform enumerations (salary categories, transfer types, property types, city tiers, professor ranks, military grades, etc.) managed when a new key is needed? → A: Fully data-driven. Enumerations live in a dedicated `PlatformEnumeration` registry (set/managed by a separate feature, planned as 003-platform-enums). This feature consumes the registry READ-ONLY: tier map keys are strings that MUST resolve to active members of the relevant enumeration. Adding a new key (e.g., a new salary category Cat-D) is a configuration change in the registry — zero code release. Bank program save-time validation queries the registry and rejects unknown keys with the specific offending key in the response.
- Q: What precision must monetary and percentage fields carry? → A: Monetary values use 13-digit precision with 2-digit scale (max value 99,999,999,999.99 EGP — defensively oversized vs the 8-figure current need). Percentage values use 7-digit precision with 4-digit scale (max value 999.9999% with 4-decimal precision, e.g., 26.5500% for stamp-duty / interest rounding). Banker's rounding for display. No floats anywhere in the pipeline.
- Q: How does the matching engine compute installments for programs whose rate is variable (e.g., CBE policy + spread, quarterly reset)? → A: Variable rates carry a free-form `variableRateNote` (operator + applicant disclosure text) AND a required numeric `currentEffectiveRate` (decimal) when variability is declared. The matching engine reads `currentEffectiveRate` as the value-of-record (it participates in the precedence cascade as the "base rate" leg for variable programs). Updating the effective rate emits a distinct audit event from updating the explanatory note. Snapshot-on-match (Principle I) preserves the rate the applicant saw at match time; later effective-rate updates do NOT mutate existing offers.
- Q: Where does the platform get the "original loan rate" for buyout-program matching, and the BKT / I-Score MOB evidence for performance-criteria gates? → A: Hybrid. Both kinds of evidence are declared by the applicant at the wizard step. When a bureau integration (Egyptian I-Score or equivalent) is configured and reachable, the platform auto-verifies the declared values at match time. When the bureau is NOT configured or unreachable, the resulting offer ships with a `selfDeclared: true` badge surfaced on the offer and the bank-program detail view; an operator validates against uploaded documents later. The matching engine treats the declared value as authoritative for the offer computation; the verification status changes only the badge/flag, not the offer math (which is snapshot at match time per Principle I).
- Q: How does the ABK 20-program seed run in production? → A: Opt-in via a super_admin-only endpoint. `prisma db seed` only creates the bootstrap super_admin (per feature 001) — it does NOT auto-seed bank programs. The 20-program catalog is created on demand via `POST /api/admin/banks/seed-abk` (super_admin only). The endpoint is idempotent (re-running skips programs with the same program code). Competitor catalogs (Bank NXT example) use a separate super_admin endpoint with the same idempotency contract.
- Q: How does the matching engine resolve `rateByDownPaymentPercent` when the applicant's down-payment percent does NOT match an exact band key (e.g., bands are 30/40/45/50/60 and applicant offers 35%)? → A: Floor-to-nearest-band-≤-applicant-value. The matching engine selects the band whose `downPaymentPercent` key is the LARGEST value ≤ the applicant's declared down-payment percent. Applicant at 35% with bands {30,40,45,50,60} resolves to the 30% band rate. If the applicant's down-payment percent is BELOW every defined band (e.g., 20% applicant against bands starting at 30%), the `rateByDownPaymentPercent` dimension produces NO match and the cascade falls through to the next level (FR-008b). The platform NEVER interpolates between bands and NEVER ceilings up to a richer-applicant tier (per Principle II — banks-are-data + cascade determinism).
- Q: How do the wealth-tier eligibility gates `minBankStatementBalanceEGP` and `minAssetsValueEGP` combine when both are configured on the same program (e.g., SF-HIGH-END = 100M bank balance AND 7M assets)? → A: AND — both gates must pass when both are configured. Either gate alone is exploitable for the wealth-tier intent; requiring both filters to genuinely-wealthy applicants. A program that wants OR-semantics expresses it by leaving one field null. The matching engine evaluates: `(minBankStatementBalanceEGP == null OR applicant.bankStatementBalance >= minBankStatementBalanceEGP) AND (minAssetsValueEGP == null OR applicant.assetsValue >= minAssetsValueEGP)`. A null gate is treated as "not configured" → does not block. Both gates non-null AND applicant fails either → program excluded from candidates.
- Q: How is the operator-discretion uplift to a higher loan ceiling (e.g., SF-SELF-EMP's 2M standard cap → 3M for strong bank-statement profiles) represented in the data model? → A: Separate field `qualitativeReviewMaxEGP` on the loan-limits sub-configuration, gated by `requiresQualitativeReview = true`. The standard `maxEGP` is the auto-grant ceiling for all qualifying applicants; the `qualitativeReviewMaxEGP` unlocks ONLY after an operator explicitly approves the offer's qualitative-review badge. Slots above `maxEGP` in the FR-008c loan-limit cascade as `maxQualitativeReviewEGP` when (and only when) the offer carries operator-approved qualitative review. The uplift transition is audit-logged with a distinct event type capturing actor, before/after ceiling, and rationale. Programs without `requiresQualitativeReview = true` MUST NOT carry a non-null `qualitativeReviewMaxEGP` (validation rejects).
- Q: How does the matching engine handle `rateByAssetValueBand` when only an upper-bound band is configured (e.g., SF-AUTO `> 4,000,000 → −1%`) and the applicant's asset value is BELOW that band (e.g., 3M car)? → A: Silent cascade fallthrough — no match. The `rateByAssetValueBand` dimension produces NO match for that application and the cascade falls through to the next FR-008b level (typically `rateBySeniority → rateByEmploymentType → baseRate`). Mirrors FR-008o.1 (down-payment band below-all-bands). Operators who want a lowest-tier catch-all MUST configure an explicit floor band (e.g., `"0"` key for cars at 0+ EGP). The cascade preview (FR-008f) labels the no-match explicitly (e.g., "asset-value band: no match (3M below 4M threshold) → fell through to rateByEmploymentType"). Platform NEVER synthesizes implicit floor bands and NEVER interpolates.
- Q: Where does the derivation chain live for tier-map values that the seed resolved from a base rate plus a delta (e.g., SF-AUTO 30 % down + car > 4M → seed-resolved 24.5 % = 25.5 % − 1 %), so the detail view does NOT render a magic absolute number? → A: Per-entry structured `derivation` field on each rate-tier-map value. Each `rateByDownPaymentPercent`, `rateByAssetValueBand`, `rateByLoanAmountBand`, and `rateByCustomerProgramTier` value MAY carry an optional `derivation: { sourceRatePercent, deltaPercent, reason }` triple. Seed routines populate it when the source notes encode a delta-from-base; admin-form entries leave it null. The detail-view cascade preview MUST render the derivation chain when present (e.g., "24.5 % (= 25.5 % from the 30 % down-payment band − 1 % high-value-car discount per `derivation.reason`)"). The matching engine NEVER reads `derivation` — only the absolute `value` participates in computation (Principle II — cascade determinism). `derivation` is documentation only and survives clones. Validation rejects a derivation triple whose stated arithmetic (`sourceRatePercent + deltaPercent`) does NOT equal the absolute `value` within ±0.0001 % — guards against drift between the chain and the persisted value.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Admin creates a new bank program from scratch (Priority: P1)

A staff member with the admin or super_admin role opens the admin dashboard, navigates to the bank programs section, and creates a brand-new loan program by completing a structured multi-section form. They enter identity (program code, bank name, friendly name), tenor configuration (minimum/maximum months, tier overrides), loan limits (minimum/maximum amounts in Egyptian Pounds, tier overrides by salary category, transfer type, property type, city tier, employment type, certificate-of-deposit value), pricing (base rate and tier-driven rates by employment type, seniority, transfer type, tenor), eligibility (accepted employment types, age range, minimum income, dozens of boolean flags, accepted salary-transfer types, debt-burden-ratio cap), income-assumption rules (one of: declared, by years in job, by professor rank, by military grade, by certificate-of-deposit value, by car installment, by credit-card limit) with the appropriate table, fees (admin fee, stamp duty, life insurance, late-payment, payoff), required documents, and free-form notes. They save. Within seconds, the new program is available for the matching engine to consider.

**Why this priority**: Bank programs are the central data of the platform — without the ability to create them via the admin dashboard, ZERO new banks can join the marketplace without a code release. This story alone delivers the value that the entire feature exists to provide: configuration without code. Without it, nothing else here matters.

**Independent Test**: Sign in as an admin. Click "Add bank program." Fill all required sections with a known-good configuration (e.g., a salaried-only personal loan for ABK Egypt, range 50,000–1,500,000 EGP, 24% rate, 36-month max). Save. Verify (a) the program appears in the list, (b) opening it reproduces every value entered, (c) a new application that fits the configured eligibility produces a matched offer from this program within one matching cycle.

**Acceptance Scenarios**:

1. **Given** the admin is on the bank programs list page, **When** they click "Add bank program" and complete every required section with valid data, **Then** the program is persisted and returned in the next list refresh.
2. **Given** the admin is creating a program with a program code that already exists, **When** they submit, **Then** the form displays a localized "this program code is already in use" error on the program-code field and the program is NOT created.
3. **Given** the admin enters a minimum loan amount greater than the maximum, **When** the field loses focus or the form is submitted, **Then** an inline localized validation error explains the constraint and the submit button remains disabled.
4. **Given** the admin selects an income-assumption type of "by professor rank," **When** the assumption section renders, **Then** ONLY the rank→income table is shown (other type-specific tables are hidden).
5. **Given** the admin partially fills the form and refreshes the browser, **When** they return to the create page, **Then** no draft is preserved (drafting is out of scope; see Assumptions).
6. **Given** the admin enters a tier override (e.g., "max loan 750,000 for salary category C") that references an enum value not recognized by the platform, **When** they submit, **Then** the server response identifies the offending field and value, and the form surfaces the error inline.
7. **Given** the admin saves a valid program, **When** the operation completes, **Then** the dashboard displays a localized success toast and an audit event is recorded with the actor, timestamp, and the resulting program identifier.
8. **Given** the admin creates a program that uses an income-surrogate strategy (e.g., `byProfessorRank`), **When** they select the strategy, **Then** the form dynamically reveals ONLY the configuration shape relevant to that strategy (rank → income map) and hides the others. Switching strategies clears the prior strategy's table to prevent stale data.
9. **Given** the admin enables `isVariableRate` on the program, **When** they save, **Then** the form requires `currentEffectiveRate` AND offers optional `spreadMinPercent` / `spreadMaxPercent` fields for the disclosure range. Saving without `currentEffectiveRate` is rejected with `INVALID_VARIABLE_RATE_CONFIGURATION`.
10. **Given** the admin configures a program with `feeWaiverEnabledAtRatePercent: 26.0` and `feeWaiverPenaltyRatePercent: 2.0`, **When** the form's what-if preview pane evaluates a sample applicant whose tier-cascade produces an effective rate of 26.5%, **Then** the preview shows "Admin fee waived (rate ≥ 26%, tenor ≥ 36 months); penalty rate +2% applied; final rate 28.5%."

### User Story 2 — Staff list, search, and view bank program details (Priority: P1)

Internal staff (admin, super_admin, viewer) need to see what bank programs currently exist, search for specific ones, filter by attributes, and open any individual program to review its full configuration in plain language. Viewing is read-only for the viewer role; create / edit / clone / toggle / delete actions are hidden or disabled accordingly.

**Why this priority**: Operational visibility into existing programs is required from day one. Without this, an admin creating a new program cannot check whether a similar program already exists, which leads to duplicate / conflicting configurations. The list page is also the entry point for every other action (edit, clone, toggle, delete) — this is structural for the feature, not an enhancement.

**Independent Test**: Seed five example programs (one per income-assumption type). Sign in as each of the three roles. Confirm each role sees the list. Confirm viewer cannot reach create, edit, clone, toggle, or delete. Confirm admin can reach create / edit / clone / toggle but not delete. Confirm super_admin can reach all actions. Click a program → see all sections populated in plain language. Apply filters; verify the list updates.

**Acceptance Scenarios**:

1. **Given** a staff member with any role signed in, **When** they visit the bank programs section, **Then** the list of programs renders with pagination metadata.
2. **Given** a viewer signed in, **When** they look at any row's action menu, **Then** no write actions (create, edit, clone, toggle, delete) are accessible from the UI, and direct backend calls for those actions are rejected with the platform's localized "forbidden" response.
3. **Given** an admin signed in, **When** they look at any row's action menu, **Then** create / edit / clone / toggle are accessible but delete is NOT (super_admin only).
4. **Given** a super_admin signed in, **When** they look at any row's action menu, **Then** all actions including delete are accessible.
5. **Given** any staff member opens a program detail page, **When** the program contains tiered rules, **Then** each rule is rendered with the tier criteria expressed in plain Arabic (or English when the dashboard is in English mode), e.g., "9% for government employees with Cat-A salary category and payroll transfer."
6. **Given** any staff member types in the search bar, **When** the input debounces, **Then** the list filters to programs whose program code or friendly name contains the entered text (case-insensitive, both languages).
7. **Given** filters are applied (e.g., active only + loan purpose = mortgage + employment type = self-employed), **When** the list refreshes, **Then** only programs matching all selected filters are returned.

### User Story 3 — Admin edits and toggles existing programs (Priority: P2)

An admin updates a program's configuration when a bank changes its rules. They can change any field except the immutable program code, and they can toggle a program active or inactive without deleting it. Toggling is reversible. **Edits to a bank program take effect for future matches only**; bank offers already created from previous configurations retain their original snapshot values.

**Why this priority**: This is operational maintenance — banks update their rules; the platform must reflect that. Lower priority than create + view because the platform can still onboard NEW banks without this, but cannot operate long-term without it.

**Independent Test**: With three programs already in the system, edit program #1's rate from 24% to 25% and save. Verify (a) the change appears on detail view, (b) any pre-existing bank offers from program #1 still report 24% (snapshot preserved), (c) any new application matched against program #1 quotes the new 25% rate. Toggle program #2 inactive; verify it disappears from matching candidates but its historical offers remain accessible from offer details.

**Acceptance Scenarios**:

1. **Given** an admin opens a program for editing, **When** they change any field except the program code and save, **Then** the change is persisted and an audit event is recorded with before/after values.
2. **Given** an admin attempts to edit the program code on an existing program, **When** the form renders, **Then** the program code field is read-only / locked.
3. **Given** an admin toggles a program inactive, **When** the matching engine next runs, **Then** the program is NOT considered for new applications until it is toggled active again.
4. **Given** an admin toggles a program inactive, **When** any user views existing bank offers that were created from that program, **Then** those offers remain accessible and display their original snapshot values.
5. **Given** the active super_admin floor invariant from feature 001 does NOT apply here (program toggles do not affect staff accounts), **When** an admin toggles the only active program of a given bank, **Then** the toggle succeeds (there is no "last active program" guard at this stage).
6. **Given** two admins open the same program for editing simultaneously, **When** both submit, **Then** the second submitter receives a localized "this program was changed by someone else; please reload" response and the first submitter's changes are NOT silently overwritten.

### User Story 4 — Admin clones an existing program (Priority: P2)

An admin uses an existing program as a template for a new one. They click "Clone" on the source program, the system prompts for a new program code, deep-copies all sub-configuration (tenor, limits, pricing, eligibility, income assumption, fees, documents, notes), and opens the new program in edit mode so the admin can tweak it.

**Why this priority**: Banks usually run dozens of similar programs (e.g., ABK-01 through ABK-20 differ only in rate, tenure, or eligibility flags). Cloning eliminates 90% of the re-entry work and dramatically lowers the error rate when onboarding bank-program variants. Lower priority than create + edit because workaround = create from scratch, but high-value efficiency lift.

**Independent Test**: Open program ABK-01. Click Clone. Enter new program code ABK-21. Confirm (a) the new program is created with every sub-field identical to ABK-01 except the program code, (b) the system navigates to the new program's edit page, (c) saving the new program persists it as a distinct entity (changing ABK-21 does NOT change ABK-01).

**Acceptance Scenarios**:

1. **Given** an admin clicks "Clone" on a source program, **When** the clone modal appears, **Then** they are prompted for a new program code (with the source program code shown for reference).
2. **Given** an admin enters a new program code that already exists, **When** they submit, **Then** the clone modal displays a localized "program code already in use" error and the clone is NOT created.
3. **Given** an admin enters a valid new program code, **When** the clone completes, **Then** every sub-field of the source program is copied into the new program EXCEPT the program code, and the dashboard navigates to the new program's edit page.
4. **Given** a clone has been created, **When** the admin later edits either the source or the clone, **Then** the changes do NOT propagate to the other (they are independent).

### User Story 5 — Super_admin deletes a program; mobile read-only API exposes active programs (Priority: P3)

A super_admin can permanently delete a bank program when it is truly retired and no longer needed for historical reference, subject to a safety guard that refuses deletion when any bank offers reference the program. Additionally, the platform exposes a read-only mobile API surface that returns the active program list and individual program detail in a shape suitable for end-user (mobile) consumption — built now so the future mobile app has a stable contract from day one.

**Why this priority**: Delete is rare and dangerous; usually programs are deactivated instead. The mobile API surface is built now to lock the contract before the mobile client exists, but it has no immediate user-facing value. Lowest priority — operational + future-proofing.

**Independent Test**: As super_admin, attempt to delete a program with existing bank offers → blocked with a localized "this program has offers; deactivate instead" response. Delete a program with no offers → succeeds and disappears from the list. From a command-line client (acting as the future mobile app), call the mobile read-only endpoint with valid request signing → receive a payload containing only active programs with reduced fields suitable for mobile rendering.

**Acceptance Scenarios**:

1. **Given** a super_admin attempts to delete a program that has zero bank offers referencing it, **When** they confirm the deletion (via a double-confirmation dialog), **Then** the program is permanently removed and an audit event is recorded.
2. **Given** a super_admin attempts to delete a program that has one or more bank offers referencing it, **When** they confirm the deletion, **Then** the request is rejected with a localized "this program has offers; deactivate instead" response, the program is NOT deleted, and the response includes the offer count so the operator can plan.
3. **Given** an admin (not super_admin) attempts to delete via direct backend call, **When** the request is received, **Then** it is rejected with the platform's localized "forbidden" response.
4. **Given** a mobile-API client (request-signed) calls the active-programs list, **When** the request is authentic and the signature is valid, **Then** the response includes ONLY programs whose active flag is true, with fields reduced to those needed for mobile rendering (no internal IDs, audit fields, or operator notes).
5. **Given** a mobile-API client requests a single program that is inactive, **When** the response is generated, **Then** the request is rejected as "not found" (inactive programs are invisible to mobile callers, regardless of program code).

### Edge Cases

- An admin saves a program with a minimum loan amount greater than its maximum: the form blocks submission and the server (if reached) rejects with a localized validation error identifying the offending fields.
- An admin saves a program with a minimum age greater than the maximum age, or with the same value at both bounds: form blocks submission and server rejects.
- An admin defines a tier override whose key is a value not in the platform's accepted enumeration for that tier type (e.g., "salary category D" when only A/B/C/outsource exist): the server identifies the unknown enum value and rejects with a clear localized message.
- An admin defines a tier override whose value is logically impossible (e.g., maxMonths = 0 or negative): rejected.
- An admin saves a program whose income-assumption type is "by professor rank" without providing the rank→income table, or "by military grade" without the grade→income table: rejected with a localized "tier configuration required for this income-assumption type" message.
- An admin tries to delete a program with thousands of dependent offers: rejected with the offer count clearly stated; the admin understands they must deactivate instead.
- Two admins open the same program for editing; both submit. The first submitter's save increments the program's version from N to N+1. The second submitter's save, sent with version N, is rejected with `CONFLICT_STALE_DATA` and the current version N+1; the dashboard prompts the operator to reload and re-apply their intended change against the current state. The first submitter's changes are NEVER silently overwritten.
- An admin pastes a monetary amount with locale-specific formatting (Arabic-Indic digits, or thousands separator): the form normalizes to the canonical numeric value before validation and submission.
- An admin lists programs while filtered to a combination that returns zero results: the empty state explains "no programs match these filters" with a clear "clear filters" affordance.
- An admin clicks Clone but the network response is delayed: the clone button enters a busy state and is non-interactive until the response arrives or fails; double-clicking does NOT create two clones.
- A viewer with the platform open in a second tab observes a program become inactive after another operator toggles it: refreshing the list reflects the change; existing detail-page views may be stale until refreshed (no live push in v1).
- The Egyptian-Pound currency symbol renders correctly in both Arabic and English modes; the input does not strip or duplicate it.
- A program's display in Arabic mode shows all monetary amounts using Egyptian Arabic conventions (numerals optionally Arabic-Indic, thousands separator per locale).
- A monetary input handles values up to 99,999,999,999.99 EGP without precision loss or truncation. Egyptian eight-figure mortgages (e.g., 25,000,000.00 EGP) round-trip without scale changes; larger commercial values up to the precision ceiling round-trip too.
- A percentage input handles values like `26.5500%` (four-decimal precision) without truncating to `26.55%`. Display formatting may shorten trailing zeros for readability but the stored value retains full precision.
- An admin configures both a base rate and a `rateByEmploymentType.salaried` override; for a salaried applicant the matching engine selects the salaried override per the cascade. If the program later adds a `rateByTenor` override matching the applicant's tenor, the tenor override wins (it sits higher in the cascade). The detail view labels which cascade level is currently active for any sample applicant the operator inspects.
- An admin configures NO tier overrides on a dimension; the platform uses the base value for every application. The detail view labels the source as "base value (no overrides match)."
- An admin opens a bank program that references an enumeration key (e.g., `maxBySalaryCategory.cat_d`) which has been DEACTIVATED in the registry since the program was last saved: the dashboard surfaces a "1 deprecated tier key — review" warning badge on the list row and a localized banner on the detail view explaining which key is deprecated; the program is NOT auto-mutated. The operator chooses whether to remove the deprecated entry or remap to an active member.
- The `PlatformEnumeration` registry is unavailable (network failure or downstream error) when the admin opens the create form: the tier-key pickers are disabled and the form displays a localized "enumerations unavailable, retry shortly" state; the admin cannot submit until the registry recovers (fail-closed — no fallback to stale or guessed enumerations).
- An admin creates a variable-rate program (`isVariableRate = true`) without supplying `currentEffectiveRate`: the form blocks submission AND the server rejects with `INVALID_VARIABLE_RATE_CONFIGURATION` identifying the missing field.
- An admin updates the `currentEffectiveRate` on a variable-rate program (e.g., after a CBE policy move): the system emits a distinct rate-update audit event capturing old → new value and operator notes. Pre-existing bank offers from that program keep their original snapshot rate; subsequent matches use the new effective rate.
- An auto-loan applicant's down-payment percent is BETWEEN two configured bands (e.g., bands {30, 40, 45, 50, 60}; applicant 35 %): the matching engine resolves to the 30-band rate (floor-to-nearest-≤-applicant per FR-008o.1). The cascade preview labels the matched band ("30 ≤ 35") so the operator can reproduce the math.
- An auto-loan applicant's down-payment percent is BELOW the lowest configured band (e.g., bands start at 30 %; applicant 20 %): `rateByDownPaymentPercent` produces no match; the cascade falls through to the next level (`rateByCustomerProgramTier → rateByAssetValueBand → … → baseRate`). Operators configuring a single-band program should explicitly add a `"0"` floor band if they want the lowest tier to catch all applicants.
- An applicant's asset value (car price, property value) is BELOW the lowest `rateByAssetValueBand` key (e.g., SF-AUTO band `>4M`; applicant car 3M): the dimension produces no match per FR-008p.1; cascade falls through to the next FR-008b level. The cascade preview labels the no-match explicitly so the operator understands why the cheaper-car rate did NOT get the −1 % discount.

## Requirements *(mandatory)*

### Functional Requirements

**Data model**

- **FR-001**: System MUST allow each bank program to carry: an immutable program code (unique across all programs), a bank name, a friendly display name, a **program-type classification** of either `income_proof` (income comes from declared salary / statements) or `income_surrogate` (income is computed by a configured rule — see FR-006), a **product-category classification** drawn from the platform enumeration (personal, mortgage, car, education, pension, secured, buyout, credit_card_cross_sell, auto_cross_sell, wealth, clubs — extensible per the FR-010 registry rule), a **currencies list** (defaults to `['EGP']`; multi-currency programs like Secured Loans declare `['EGP', 'USD', 'EUR']`), an active/inactive flag, lists of required documents, free-form operator notes, and a separate list of operator tips for internal guidance (distinct from end-user-facing notes).
- **FR-002**: System MUST allow each bank program to carry a tenor configuration consisting of minimum and maximum months, optional per-salary-category tenor overrides (Cat-A / Cat-B / Cat-C / outsource), and optional per-employment-type tenor overrides (salaried / self-employed).
- **FR-003**: System MUST allow each bank program to carry loan-limit configuration consisting of minimum and maximum loan amounts (in the program's primary currency; programs that quote in multiple currencies record separate min/max per declared currency), optional per-salary-category maximums, optional per-salary-transfer-type maximums, optional per-property-type maximums (for mortgage and compound-owner products), optional per-city-tier maximums (e.g., main-cities vs other-cities for doctor programs), optional per-employment-type maximums, optional per-certificate-of-deposit-value tiered maximums (a list of bands), an optional per-performance-tier maximum (e.g., 6 / 12 / 18 / 24 months-on-book → escalating loan ceiling for buyout programs), an optional top-up maximum, an optional **loan-to-value (LTV) ceiling** for secured products (percentage cap on collateral value, e.g., 95%), an optional separate "other cities" override for products that cap rural loans tighter than the main-cities maximum, and an optional **`qualitativeReviewMaxEGP`** ceiling (decimal, nullable) that unlocks a higher loan amount than `maxEGP` ONLY when an operator approves the offer's qualitative-review badge (see FR-003a + FR-005c).
- **FR-003a**: `qualitativeReviewMaxEGP` semantics. (a) Non-null `qualitativeReviewMaxEGP` is permitted ONLY on programs whose eligibility carries `requiresQualitativeReview = true`; validation rejects with `INVALID_QUALITATIVE_REVIEW_CEILING` otherwise. (b) `qualitativeReviewMaxEGP` MUST be strictly greater than `maxEGP` (it is an uplift, not a downgrade); validation rejects with `QUALITATIVE_REVIEW_CEILING_BELOW_BASE` when violated. (c) At match time the candidate program's effective loan ceiling = `maxEGP` (the auto-grant cap). The matching engine MUST NOT apply `qualitativeReviewMaxEGP` proactively. (d) When the resulting offer carries the qualitative-review badge AND an operator explicitly approves the badge via the offer-review surface, the offer's effective loan ceiling lifts from `maxEGP` to `qualitativeReviewMaxEGP` for that single offer. The transition emits a distinct audit event capturing actor, program code, offer identifier, before/after ceiling, and free-form rationale. (e) Operator denial of the qualitative-review badge keeps the offer's ceiling at `maxEGP`. (f) `qualitativeReviewMaxEGP` is NOT a cascade tier — it is a per-offer ceiling lift gated by operator approval. SF-SELF-EMP example: `maxEGP = 2,000,000`, `qualitativeReviewMaxEGP = 3,000,000`, `requiresQualitativeReview = true`. All qualifying applicants start at 2M; operator approval lifts to 3M.
- **FR-004**: System MUST allow each bank program to carry pricing configuration consisting of: an optional base annual rate, optional per-employment-type rate overrides, optional per-salary-transfer-type rate overrides (including payroll-by-salary-category permutations like `payroll_cat_a`, `payroll_cat_b`, `payroll_cat_c`, plus `salary_transfer_letter`, `income_transfer_letter`, etc.), optional per-tenor rate overrides (bucketed, e.g., "1–6 years → 27%, 7 years → 29%"), optional per-tenor-and-customer-type rate overrides (e.g., Bank-NXT-style `salaried_lt_5y` vs `salaried_gt_5y`), optional per-seniority rate overrides, an `isVariableRate` boolean flag, an optional free-form `variableRateNote` (operator + applicant disclosure text, e.g., "CBE policy rate + 3%, reviewed quarterly"), an optional `currentEffectiveRate` decimal (REQUIRED when `isVariableRate` is true — see FR-011a), optional **variable-rate spread bounds** (`spreadMinPercent`, `spreadMaxPercent` — used for secured loans whose rate quoted to applicants is presented as a range), an optional **buyout rate delta** (`buyoutRateDeltaPercent`, e.g., `-3.0` meaning "subtract 3 from the bought-out loan's rate") and an optional **buyout rate minimum floor** (`buyoutRateMinFloorPercent`, e.g., `25.0` — the rate cannot drop below this even after the delta), an optional **fee-waiver penalty rate** (`feeWaiverPenaltyRatePercent`, default 2.0 — added to the effective rate when admin fees are waived AND the loan tenor meets the penalty threshold), an optional **fee-waiver penalty minimum tenor** (`feeWaiverPenaltyMinTenorMonths`, default 36 — only loans of at least this tenor trigger the penalty), an optional **admin-fee-waiver rate threshold** (`feeWaiverEnabledAtRatePercent` — admin fees are waived when the program's effective rate is at or above this value), and an optional **admin-fee-waiver minimum tenor** (`feeWaiverMinTenorMonths`). When `isVariableRate` is true, `currentEffectiveRate` MUST be provided and acts as the program's effective rate-of-record (taking the place of `baseRate` in the FR-008b precedence cascade). When `isVariableRate` is false, `currentEffectiveRate` MUST be empty and `baseRate` is the rate-of-record.
- **FR-005**: System MUST allow each bank program to carry eligibility rules including: accepted employment types (salaried, self-employed, or both), age range (with separate optional bounds for self-employed), minimum monthly income (with a separate optional minimum for self-employed), minimum time in job (in months or years), optional per-salary-category minimums for time in job, accepted loan purposes, the platform's debt-burden-ratio cap (defaults to 50%), a `skipDbrCheck` boolean flag (defaults false; secured loans set this true since the loan is collateralized), accepted salary-transfer types, and the following boolean / typed eligibility flags (each independently configurable per program, all defaulting to false unless noted):
  - `requiresCD`, `requiresAutoLoanAtABK`, `requiresAutoLoanAtOtherBank`, `requiresCreditCardAtOtherBank`, `requiresCompoundProperty`, `requiresCollateral`, `requiresClubMembership`, `requiresExistingLoan` (for buyout), `requiresFRMUVerification` (for football / compound verification)
  - `minimumCreditCardHoldingMonths` (integer, nullable — e.g., 6 for the credit-card cross-sell program)
  - `competitorCardMustBeUnsecured` (boolean)
  - `eligibleCarPriceMinEGP` (decimal, nullable — for car cross-sell programs that gate on car value)
  - `eligibleDownPaymentPercent` (decimal, nullable — minimum down payment percent required)
  - `clubClass` (string, nullable — e.g., "Class 1" for football)
  - `compoundClass` (string, nullable — e.g., "High End" for villa loans)
  - `companyType` (enumeration array, nullable — e.g., `['commercial_bank', 'public_bank']` for the Bankers program)
  - `commercialBankIncomePercent`, `publicBankIncomePercent` (decimals, e.g., 80% vs 100% — Bankers program quotes different income haircuts depending on whether the applicant works at a commercial or public-sector bank)
- **FR-005a**: Each bank program MAY carry a separate Performance Criteria sub-configuration governing customer-history gates (used by buyout and cross-sell programs). See FR-005b and the "Performance Criteria" entity in Key Entities.
- **FR-005b**: Performance Criteria configuration includes: `requiredMOBMonths` (minimum months-on-book to qualify), `iScoreMOBPerformanceCheck` (boolean — whether to gate on I-Score MOB), `bkt1NoHitWithinMonths` (integer, nullable — no bucket-1 hit within the last N months), `bkt2NoHitWithinMonths` (integer, nullable — no bucket-2 hit within the last N months), and `requireCurrentLoanStatus` (boolean — applicant must have a currently-active loan that satisfies the performance gate). The matching engine evaluates these gates against the applicant's **hybrid-sourced** credit-history evidence: the applicant declares values at the wizard step, AND when a bureau integration is configured and reachable the platform auto-verifies. When the bureau is unavailable the offer ships with `selfDeclared: true` set on the offer and a "self-declared — pending verification" badge surfaced on the offer detail and the bank-program detail view; operators validate later from uploaded documents. The declared values are authoritative for the offer math; verification status only changes the badge.
- **FR-006**: System MUST allow each bank program to declare exactly one income-assumption strategy from this extensible set (resolved against the platform enumeration registry per FR-010): `declared` (applicant-provided), `byYearsInJob`, `byProfessorRank`, `byMilitaryGrade`, `byYearsInPractice` (for doctors / professionals — tiered by years practising), `byCDValue`, `byCarInstallment` (e.g., 3× the applicant's existing car installment), `byCarLoanAmount` (e.g., 10% of the applicant's existing auto loan amount — whichever yields less when both byCarInstallment and byCarLoanAmount are configured), `byCreditCardLimit` (e.g., half the credit card limit), `byBankStatementPercent` (e.g., 30% of the applicant's bank-statement average). The chosen strategy MUST carry the configuration table appropriate to its type:
  - `byYearsInJob` / `byYearsInPractice`: an `incomeTable` array of `{ minYears, maxYears, incomeEGP }` bands.
  - `byProfessorRank`: a `rankIncomeMap` keyed by the platform's professor-rank enumeration → income.
  - `byMilitaryGrade`: a `gradeIncomeMap` keyed by the platform's military-grade enumeration → income.
  - `byCDValue`: an `incomeTable` of CD-value bands → assumed monthly income, OR a `cdIncomePercent` of the CD balance with a `cdIncomeMinEGP` floor and an optional `cdIncomePercentOfDeposits` ceiling (whichever yields less).
  - `byCarInstallment`: a `carInstallmentMultiplier` (e.g., 3.0).
  - `byCarLoanAmount`: a `carLoanAmountPercent` (e.g., 10.0).
  - `byCreditCardLimit`: a `creditCardLimitMultiplier` (e.g., 0.5).
  - `byBankStatementPercent`: a `bankStatementPercent` (e.g., 30.0).
  When the strategy combines two formulas with a "whichever yields less / more" rule (e.g., byCDValue with both percent-of-CD and percent-of-deposits), the rule MUST be explicitly declared on the configuration (`combinationRule: 'lesser_of' | 'greater_of'`).
- **FR-007**: System MUST allow each bank program to carry a fees configuration including: admin-fee percentage (or zero for fee-free programs like CD-holders), an `adminFeeDisplay` human-readable string (e.g., "0% — waived for CD holders"), an optional admin-fee range (`adminFeeRangeMin` / `adminFeeRangeMax` — used by secured loans that quote a fee range like "0.5% to 1%"), stamp-duty percentage (default 0.5), life-insurance percentage (default 0.5), `lifeInsuranceMandatory` flag (true for pensions), an optional `lifeInsuranceMinLoanEGP` threshold (e.g., 1.5M for self-employed — insurance only mandatory above this amount), late-payment-fee percentage (default 4.0, applied on top of the loan rate), payoff-cash percentage (default 12.0), payoff-buyout percentage (default 15.0), and optional flat collateral-management fees (`collateralReplacementFeeEGP`, `collateralDecreaseFeeEGP` — for secured loans).
- **FR-008**: System MUST store all monetary amounts as decimal values with precision 13 and scale 2 (maximum value 99,999,999,999.99 EGP). All percentage values are stored as decimal values with precision 7 and scale 4 (maximum value 999.9999%, four-decimal precision for the stamp-duty / interest-rounding cases Egyptian banks publish). NO float / double types are permitted in the storage, transport, validation, or computation pipeline. Display formatting uses banker's rounding and respects Egyptian Arabic conventions in Arabic mode and English conventions in English mode.

**Additional rate-tier dimensions (surfaced by sales-floor catalog)**

- **FR-008o**: System MUST allow each bank program's pricing configuration to carry an optional `rateByDownPaymentPercent` tier map keyed by down-payment-percent bands (e.g., `{ "30": 25.5, "40": 23.5, "45": 22.5, "50": 22.25, "60": 21.75 }` for an auto-loan program where higher down payment buys a lower rate). The map MUST be evaluated as part of the pricing precedence cascade, slotted above `rateByEmploymentType` and below `rateByTransferType` in the standard cascade order, when the program declares a down-payment-tiered rate.
- **FR-008o.1**: `rateByDownPaymentPercent` resolution rule = floor-to-nearest-band-≤-applicant-value. The matching engine selects the band whose key is the LARGEST band ≤ the applicant's declared down-payment percent. Example: bands {30, 40, 45, 50, 60}; applicant 35 % → 30 band (25.5 %); applicant 44 % → 40 band (23.5 %); applicant 60 % → 60 band (21.75 %); applicant 65 % → 60 band (21.75 %). When the applicant value is BELOW every defined band (e.g., 20 % against bands starting at 30 %), `rateByDownPaymentPercent` produces NO match and the cascade falls through to the next FR-008b level. The platform NEVER interpolates and NEVER ceilings up. Detail-view cascade preview (FR-008f) MUST label the matched band explicitly (e.g., "Rate cascade: 25.5 % (down-payment band 30 ≤ applicant 35) — fee waiver: n/a").
- **FR-008p**: System MUST allow each bank program to carry an optional `rateByAssetValueBand` or `rateByLoanAmountBand` tier map keyed by ranges of underlying asset value (cars, properties) or loan amount (e.g., car price > 4,000,000 EGP → −1% from base rate). When configured, the band MUST be expressed as an ABSOLUTE rate, NOT as a delta — the matching engine selects the band's effective rate via the cascade. (Deltas / discounts off a base rate are computed at admin-config time, not at match time, to preserve cascade determinism.)
- **FR-008p.1**: `rateByAssetValueBand` and `rateByLoanAmountBand` resolution rule = floor-to-nearest-band-≤-applicant-value (same family as FR-008o.1). The matching engine selects the band whose key (lower bound of the range) is the LARGEST value ≤ the applicant's asset value (or loan amount). Example: bands {`4000000` → 24.5} only; applicant car 3,000,000 → NO match (3M < 4M) → cascade falls through to the next FR-008b level. Applicant car 5,000,000 → 4000000 band selected (24.5 %). Operators who want a catch-all lowest tier MUST configure an explicit floor band (e.g., `"0"` key). The platform NEVER synthesizes implicit floor bands, NEVER interpolates, and NEVER ceilings up. The detail-view cascade preview MUST label no-match outcomes (e.g., "asset-value band: no match (3M below 4M threshold) → fell through to `rateByEmploymentType`").
- **FR-008s**: Tier-map values for `rateByDownPaymentPercent`, `rateByAssetValueBand`, `rateByLoanAmountBand`, and `rateByCustomerProgramTier` MAY each carry an optional structured `derivation` field shaped `{ sourceRatePercent: decimal(7,4), deltaPercent: decimal(7,4), reason: string }`. Purpose: preserve the human-readable derivation chain for seed-resolved values (e.g., SF-AUTO 30 % down + car > 4M → 24.5 % = 25.5 % − 1 %) so the detail view renders the math, not a magic number. (a) The matching engine MUST IGNORE `derivation` at match time and operate ONLY on the absolute `value` (Principle II — cascade determinism). (b) The detail-view cascade preview (FR-008f) MUST render the derivation chain when `derivation` is non-null (e.g., "24.5 % (= 25.5 % from the 30 % down-payment band − 1 % high-value-car discount: 'car price exceeds 4M threshold')"). (c) `derivation` survives clones unchanged. (d) Validation MUST reject any tier value whose `derivation.sourceRatePercent + derivation.deltaPercent` does NOT equal the absolute `value` within ±0.0001 % — guards against silent drift between persisted chain and persisted value. (e) `derivation` is OPTIONAL — admin-form entries with no documented chain leave it null and the detail view renders the absolute value alone.
- **FR-008q**: System MUST allow each bank program to carry an optional `rateByCustomerProgramTier` tier map (e.g., Blue, Plus, Wealth — keyed against a customer-program-tier enumeration in the platform registry per FR-010). This dimension slots above `rateByEmploymentType` in the cascade.
- **FR-008r**: System MUST allow each bank program to carry an **insurance-waiver penalty** rule distinct from the admin-fee-waiver penalty: `insuranceWaiverPenaltyRatePercent` (default 2.0) and `insuranceWaiverPenaltyMinTenorMonths` (default 36). When the resulting offer has mandatory life or lease insurance waived AND the matched tenor meets the threshold, the penalty rate MUST be added to the offer's effective rate AT MATCH TIME and snapshot onto the offer. The admin-fee waiver penalty (FR-008k) and the insurance waiver penalty stack independently: an offer that waives BOTH admin fees AND insurance on a long-tenor loan accrues BOTH penalty rates.

**Wealth-tier eligibility gates (surfaced by High-End notes)**

- **FR-005c**: System MUST allow each bank program to carry optional **wealth-gate eligibility fields**: `minBankStatementBalanceEGP` (decimal, nullable — minimum average bank-statement balance the applicant must demonstrate, e.g., 100,000,000 for High-End programs), `minAssetsValueEGP` (decimal, nullable — minimum declared assets value), and a `requiresQualitativeReview` boolean flag indicating the program admits applicants subject to operator judgement of bank-statement quality even when numeric thresholds are met. Programs that set `requiresQualitativeReview = true` MUST surface this on the resulting offer with a "pending operator review" badge analogous to the `selfDeclared` badge from FR-005b.
- **FR-005c.1**: Wealth-gate combination rule = AND. When BOTH `minBankStatementBalanceEGP` AND `minAssetsValueEGP` are configured (non-null) on a program, the applicant MUST satisfy BOTH gates to be considered a candidate: `applicant.bankStatementBalance ≥ minBankStatementBalanceEGP` AND `applicant.assetsValue ≥ minAssetsValueEGP`. A null gate is treated as "not configured" — it does not block. A program that wants OR-semantics expresses it by leaving one field null and pre-deciding which gate is authoritative. Failure of either configured gate excludes the program from the application's candidate set and the exclusion is logged with the failing-gate name for operator diagnostics. SF-HIGH-END (100M bank-statement AND 7M assets) MUST therefore require BOTH conditions; an applicant with 100M bank-statement but 3M assets is NOT eligible.
- **FR-005d**: System MUST allow each bank program to carry a **`requiresNoDocuments`** boolean flag (default false) indicating the program does NOT require income documents from the applicant (e.g., the "Blue / Plus" no-docs lending tier). Programs with `requiresNoDocuments = true` MUST still respect the configured `loanLimits` ceiling — typically much lower than document-backed programs (e.g., 760,000 EGP). The matching engine treats `requiresNoDocuments` programs as a separate candidate pool from document-backed programs; applicants who do not upload income documents are matched ONLY against `requiresNoDocuments` programs.

**Multi-currency support**

- **FR-008g**: Bank programs that quote in multiple currencies (e.g., Secured Loans in EGP/USD/EUR) MUST record min/max loan amount, base rate, and effective rate PER currency where those values differ across currencies. The currencies list declared on the program (FR-001) MUST be the source of truth for which currency-specific records the validation layer requires.
- **FR-008h**: Currency MUST be opaque from the matching engine's perspective: the engine selects an offer in the currency the applicant requests; if the applicant requests a currency the program does not support, the program is excluded from candidates for that application.
- **FR-008i**: Display formatting MUST respect each currency's locale conventions (Egyptian Pounds formatted per the Egyptian Arabic norms in Arabic mode, USD/EUR using their respective standards). Persistence stores the canonical currency code (ISO 4217) alongside each amount.

**Fee-waiver mechanics**

- **FR-008j**: When a bank program has the **fee-waiver-at-rate-threshold** rule configured (`feeWaiverEnabledAtRatePercent`), and an application's effective rate for the program (computed via the FR-008b cascade) is greater than or equal to that threshold AND the matched tenor meets the `feeWaiverMinTenorMonths` requirement, the platform MUST mark admin fees as WAIVED on the resulting bank offer. The fee waiver MUST be visible on the offer detail surface.
- **FR-008k**: When a bank program has the **fee-waiver penalty** rule configured (`feeWaiverPenaltyRatePercent`) and the resulting offer has admin fees waived (per FR-008j or any other waiver path) AND the matched tenor is at or above `feeWaiverPenaltyMinTenorMonths`, the platform MUST add the penalty rate to the offer's effective rate. The penalty is applied AT MATCH TIME and snapshot onto the offer; subsequent program edits do not re-apply.
- **FR-008l**: Both fee-waiver rules MUST be observable in the bank-program detail view's cascade preview (per FR-008f) — operators see which sample applicants trigger waiver, penalty, both, or neither.

**Buyout-rate computation**

- **FR-008m**: For programs with the buyout-rate-delta rule (`buyoutRateDeltaPercent` configured), the matching engine MUST compute the effective rate as `original_loan_rate + buyoutRateDeltaPercent`, clamped to a floor of `buyoutRateMinFloorPercent`. The "original loan rate" input is **hybrid-sourced**: the applicant declares it at the wizard step, and when a bureau integration is configured and reachable the platform auto-verifies the declared value at match time. When the bureau is unavailable the resulting offer ships with `selfDeclared: true` set and a "self-declared — pending verification" badge; operators validate later. The declared value is authoritative for the offer math regardless of verification status. The computed result substitutes for `baseRate` in the FR-008b cascade for that program.
- **FR-008n**: Bank-program detail view MUST render the buyout formula visibly (e.g., "Effective rate = original loan rate − 3%, never below 25%") so operators can reproduce the math.

**Tier precedence (selection rule)**

- **FR-008a**: For every tiered dimension, the platform MUST select exactly ONE source value at evaluation time using a deterministic precedence cascade: first matching tier wins; if no tier matches, fall back to the base value. The platform MUST NEVER compose / multiply / blend tier sources.
- **FR-008b**: Pricing (rate) precedence cascade: `rateByTenor → rateByTransferType → rateByDownPaymentPercent → rateByCustomerProgramTier → rateByAssetValueBand → rateByLoanAmountBand → rateBySeniority → rateByEmploymentType → baseRate-or-currentEffectiveRate`. The first cascade level whose key matches the application's attributes yields the rate. When the program is variable-rate (`isVariableRate = true`), `currentEffectiveRate` substitutes for `baseRate` at the bottom of the cascade. The cascade is FROZEN at the platform level per FR-008e — programs select which levels they USE; they cannot reorder.
- **FR-008c**: Loan-limit precedence cascade: `maxByCDTier → maxByPropertyType → maxByCityTier → maxByTransferType → maxBySalaryCategory → maxByEmploymentType → maxEGP`. Top-up loans use `maxTopUpEGP` independently of this cascade.
- **FR-008d**: Tenor precedence cascade: `maxMonthsBySalaryCategory → maxMonthsByEmploymentType → maxMonths`.
- **FR-008e**: The platform's accepted precedence cascade is FROZEN; bank programs configure values within the cascade but cannot reorder the cascade itself. Reordering requires a constitutional amendment.
- **FR-008f**: Detail and edit views MUST render the precedence cascade visibly for each tiered dimension so operators understand which override wins. Example display: "Rate cascade: 23% (by tenor 60 months) → 22% (salaried) → 24% (base). Effective rate: 23%."

**Validation**

- **FR-009**: System MUST enforce, at the validation boundary, that minimum loan amount is strictly less than maximum loan amount, minimum age is strictly less than maximum age, and minimum months in job is non-negative.
- **FR-010**: System MUST enforce that every tier override key resolves to a currently-active member of the platform's data-driven enumeration registry for that tier type. An unknown or inactive enum key MUST be rejected with a clear, localized response identifying the offending field, the offending key, and the active membership of the relevant enumeration.
- **FR-010a**: Tier map keys MUST be stored as opaque strings (NOT as backend-language enum types). The platform's matching engine and bank-program dashboard MUST resolve those keys against the enumeration registry at evaluation / render time. Adding, deactivating, renaming, or merging an enumeration member is a configuration change in the enumeration registry — NOT a change to this feature.
- **FR-010b**: When the bank-program create / edit form renders a tier-key picker (e.g., the dropdown for "salary category" inside a `maxBySalaryCategory` tier entry), the dashboard MUST populate the dropdown from the live enumeration registry; recently-added enumeration members MUST appear without a code release.
- **FR-010c**: If an existing bank program references an enumeration key that has since been deactivated in the registry, the platform MUST surface a deprecation warning on the detail view and on the bank program list (e.g., a yellow badge "1 deprecated tier key — review"), but MUST NOT auto-mutate the program. The operator decides whether to remove or remap.
- **FR-011**: System MUST enforce that the configuration table of the chosen income-assumption strategy is present and structurally valid for its type (e.g., a rank→income table is required when the strategy is "by professor rank").
- **FR-011a**: System MUST enforce the variable-rate consistency rule from FR-004: when `isVariableRate` is true, `currentEffectiveRate` is REQUIRED and `baseRate` is OPTIONAL; when `isVariableRate` is false, `baseRate` is REQUIRED and `currentEffectiveRate` MUST be empty. Saves violating this rule are rejected with `INVALID_VARIABLE_RATE_CONFIGURATION` identifying the offending field combination.
- **FR-012**: System MUST enforce that the program code is unique across all programs; attempting to create a program with a duplicate program code MUST be rejected with the platform's localized "program code already in use" response.
- **FR-013**: System MUST surface validation errors at the field level in the form, with each error localized in the active dashboard language. Server-returned validation errors MUST map back to the same fields the user can correct.

**List, view, filter, search**

- **FR-014**: System MUST allow internal staff to list bank programs with pagination, returning the page size, page number, and total count.
- **FR-015**: System MUST allow staff to filter the list by bank name, active/inactive status, accepted loan purpose, and accepted employment type. Filters combine with AND semantics.
- **FR-016**: System MUST allow staff to search the list with a free-text query that matches the program code or friendly display name, case-insensitively, in both languages.
- **FR-017**: System MUST allow staff to open any individual program's full configuration view, which renders every tier rule in plain Arabic (or English when the dashboard is in English mode).

**Create + edit**

- **FR-018**: Staff with the admin or super_admin role MUST be able to create a new bank program by completing the multi-section form and submitting it; the program is persisted atomically and is immediately available to the matching engine for new applications.
- **FR-019**: Staff with the admin or super_admin role MUST be able to edit any field of an existing program EXCEPT its program code; edits take effect for FUTURE matches only.
- **FR-020**: System MUST ensure that edits to a bank program do NOT mutate any bank offers already created from that program; previously created offers retain their original snapshot values (constitution Principle I).
- **FR-021**: System MUST prevent silent overwrites when two admins edit the same program simultaneously. Each bank program MUST carry an integer `version` field that increments by one on every persisted save (create, edit, toggle, clone-as-source-no-change). The dashboard MUST load the version with the program detail and submit it on save. The backend MUST compare-and-swap atomically: if the submitted version does not equal the current persisted version, the save is REJECTED with `CONFLICT_STALE_DATA`, and the response MUST include the current version so the dashboard can prompt the operator to reload.
- **FR-021a**: The version field MUST be visible neither in the mobile read-only API nor in audit event payloads addressed to operators — it is an internal correctness primitive, not a user-facing concept. The dashboard MAY expose it for debugging in a developer-mode disclosure but MUST NOT surface it as part of the form.

**Clone**

- **FR-022**: Staff with the admin or super_admin role MUST be able to clone an existing program. The clone operation MUST prompt for a new program code, copy every sub-configuration from the source, and persist the clone as an independent entity (changes to either side do not propagate to the other).
- **FR-023**: System MUST validate the new program code on clone against the same uniqueness rule that applies on create (FR-012).

**Toggle active/inactive**

- **FR-024**: Staff with the admin or super_admin role MUST be able to toggle a program's active flag. Toggling is reversible.
- **FR-025**: The matching engine MUST exclude inactive programs from candidate selection. Bank offers previously created from a now-inactive program MUST remain accessible and unchanged.

**Delete (super_admin only)**

- **FR-026**: Staff with the super_admin role MUST be able to permanently delete a bank program. Staff with the admin role MUST NOT be able to delete.
- **FR-027**: System MUST refuse deletion when one or more bank offers reference the program. The refusal response MUST include the offer count so the operator can plan (deactivate instead).
- **FR-028**: System MUST require a double confirmation for deletion (e.g., a confirmation dialog plus typing the program code to confirm).

**Mobile read-only API surface**

- **FR-029**: System MUST expose a read-only mobile endpoint returning the list of currently active programs in a shape suitable for mobile rendering (reduced fields: no internal IDs, no audit fields, no operator notes, no version metadata). The endpoint MUST authenticate the mobile client (request signing) consistent with the platform's mobile API authentication mechanism.
- **FR-030**: System MUST expose a read-only mobile endpoint returning a single active program by program code. Inactive programs MUST be invisible to mobile callers (returned as "not found" rather than disclosing their existence).

**Audit + observability**

### Key Entities *(include if feature involves data)*

- **BankProgram**: The top-level configuration entity for a single loan product offered by a bank. Carries the immutable program code, bank name, friendly display name, active/inactive flag, required-document list, free-form operator notes, an integer `version` field (increments on every persisted save for optimistic concurrency control — see FR-021), and references (one-to-one) to each sub-configuration entity below. A bank program is the unit of activation, cloning, and deletion. Constitutional immutability rule (Principle I) applies via downstream bank offers — bank offers snapshot bank-program values at match time and are not mutated when the source program changes.
- **Tenor Configuration**: The set of rules governing how long the loan can run. Carries platform-wide minimum and maximum months, plus optional per-salary-category and per-employment-type maximum-month overrides.
- **Loan-Limits Configuration**: The set of rules governing the minimum and maximum loan amount the program will offer. Carries platform-wide bounds in Egyptian Pounds, plus optional overrides by salary category, salary-transfer type, property type (mortgage only), city tier, employment type, certificate-of-deposit value (tiered bands), and an optional `qualitativeReviewMaxEGP` uplift ceiling (gated by `requiresQualitativeReview = true` on eligibility per FR-003a — unlocked only after operator approval of the offer's qualitative-review badge).
- **Pricing Configuration**: The set of rules governing the program's annual interest rate. Carries an `isVariableRate` flag, an optional base rate (fixed-rate programs), an optional `currentEffectiveRate` (variable-rate programs), an optional `variableRateNote`, optional `spreadMinPercent` / `spreadMaxPercent` (for variable-rate programs that quote a range to applicants like "spread 2% to 4%"), optional `buyoutRateDeltaPercent` and `buyoutRateMinFloorPercent` (for buyout programs), optional `feeWaiverPenaltyRatePercent` / `feeWaiverPenaltyMinTenorMonths` (the +2% penalty when admin fees are waived on long-tenor loans), optional `feeWaiverEnabledAtRatePercent` / `feeWaiverMinTenorMonths` (admin-fee-waiver thresholds), plus optional overrides by employment type, seniority, salary-transfer type (with payroll-by-salary-category permutations), and tenor (including bucketed and customer-type-bucketed forms). The note documents the variability mechanism but does NOT participate in computation — only the numeric rate-of-record does.
- **Performance Criteria Configuration**: The set of customer-history gates the program enforces (used by buyout and cross-sell programs). Carries `requiredMOBMonths` (minimum months-on-book), `iScoreMOBPerformanceCheck` (boolean), `bkt1NoHitWithinMonths` / `bkt2NoHitWithinMonths` (delinquency-bucket no-hit windows), and `requireCurrentLoanStatus` (must have an active loan satisfying the gates). The platform evaluates these gates against the applicant's credit-history evidence at match time; the evidence source is governed by a separate specification (see Assumptions).
- **Eligibility Configuration**: The set of rules governing which applications are eligible for the program. Carries accepted employment types, age range (with optional self-employed-specific bounds), minimum monthly income (with optional self-employed-specific value), minimum time in job, accepted loan purposes, the debt-burden-ratio cap, accepted salary-transfer types, and a set of boolean flags governing program-specific requirements.
- **Income-Assumption Configuration**: The single rule the program uses to determine an applicant's qualifying income when income is not declared explicitly. Carries one strategy from {declared, byYearsInJob, byProfessorRank, byMilitaryGrade, byCDValue, byCarInstallment, byCreditCardLimit} and the configuration table appropriate to that strategy.
- **Fees Configuration**: The set of fee percentages the program charges. Carries admin-fee percent (and human-readable display), stamp duty, life-insurance percent + mandatory flag, late-payment percent, payoff-cash percent, payoff-buyout percent.
- **BankProgram Audit Event**: An append-only record of an operationally-relevant change to a bank program. Captures actor identifier, program code, event type (created / updated / toggled / cloned / deleted), timestamp, source network address, correlation identifier, and a structured payload describing the change (e.g., before / after values for updates).
- **Platform Enumeration (consumed read-only)**: A data-driven registry of all platform-defined enumeration members (salary categories, salary-transfer types, employment types, loan purposes, property types, city tiers, professor ranks, military grades, and any future additions). Each entry carries an opaque enumeration-type identifier, a member-key string, a localized display label per supported locale, an active flag, and a deprecated flag. THIS feature consumes the registry READ-ONLY; management (add / deactivate / rename / merge) is owned by a separate feature (planned as 003-platform-enums). When the registry is unavailable, the bank-program edit form MUST disable tier-key pickers and display a localized "enumerations unavailable, retry shortly" state rather than fall back to stale data.

## Assumptions

- The matching engine, bank-offer entity, and downstream offer-immutability behavior are introduced in a separate specification; this specification ASSUMES the engine consumes bank-program configuration read-only and respects FR-020 by snapshot-on-match.
- Draft autosave for the create / edit form is NOT in scope; the admin completes the form in a single session OR loses unsaved work on navigation.
- Bulk import / export of bank programs (CSV / JSON ingestion) is NOT in scope; out-of-scope per the user description.
- An approval workflow (admin proposes change, super_admin approves) is NOT in scope; admins can edit directly.
- Tier-conflict detection ACROSS bank programs (e.g., flagging when two programs offer materially overlapping eligibility but very different rates) is NOT in scope.
- A public-facing comparison page (consumer-side) is NOT in scope; mobile read-only endpoints exist but the consumer surface is governed by separate mobile specifications.
- This feature ASSUMES the existence of a separate `PlatformEnumeration` registry that holds all data-driven enumerations (salary categories, salary-transfer types, employment types, loan purposes, property types, city tiers, professor ranks, military grades, plus any new additions). The registry is managed by a separate feature (planned as 003-platform-enums). This feature CONSUMES the registry read-only: tier map keys are opaque strings that resolve against the registry at validation, evaluation, and render time. Adding a new enumeration member (e.g., new salary category Cat-D) is a configuration change in the registry, NOT a code release for this feature. The seed step for this feature ASSUMES a working enumeration registry already supplies the initial Cat-A/B/C/outsource salary categories, payroll/letter/income/none transfer types, salaried/self_employed employment types, personal/car/mortgage loan purposes, apartment/twin_house/villa property types, the professor ranks, and the military grades; if the registry is empty at install time, the seed for this feature fails fast with a clear error.
- This feature ASSUMES the seed step creates a minimum of FIVE example programs covering the full diversity of income-assumption strategies (government, self-employed, professor-rank, military-grade, certificate-of-deposit-backed) so that the matching engine and downstream screens have realistic test fixtures from day one.
- This feature DOES support multi-currency programs (EGP / USD / EUR) for products that quote in multiple currencies (Secured Loans being the canonical example). Currency is per-program (declared in the `currencies` list) and per-amount (each monetary record carries its currency code). The Egyptian Pound is the DEFAULT currency for new programs.
- The applicant-side evidence required by **performance-criteria** gates (BKT history, I-Score MOB) and by **buyout-rate** computation (the original loan's rate) is sourced via a **hybrid** mechanism: declared by the applicant at the 5-step wizard, optionally auto-verified by a bureau integration (Egyptian I-Score or equivalent) when configured and reachable. When the bureau is unavailable, the offer ships with a `selfDeclared: true` flag and a "pending verification" badge; operators validate from uploaded documents post-match. The matching engine treats the declared value as authoritative for the offer math (which is snapshot at match time per Principle I); verification only changes the badge. The wizard-side capture and bureau-integration plumbing are governed by a separate specification.
- The "what-if" preview helper (FR-033e) is OPTIONAL polish; if scope-constrained, it MAY be deferred to a follow-up feature without violating other FRs.
- Side-by-side program comparison view (admin selects 2–3 programs to compare configurations) is OUT OF SCOPE for this feature; it is a candidate for a later operator-tooling feature.
